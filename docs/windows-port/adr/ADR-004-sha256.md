# ADR-004: SHA-256 (and SHA-1) without CryptoKit — a portable Swift implementation in AgentHUDSupport

- Status: accepted (M0, 2026-10-16)

## Context

CryptoKit exists only on Apple platforms. It is used in four places:

| File | Use |
| --- | --- |
| `AgentHUDSupport/RecordCoding.swift` | `SHA256.hash` of length-prefixed components: every record id (design invariant "identical on every machine") |
| `AgentHUDCore/Providers/Grok/GrokBotSessions.swift` | `SHA256.hash` of a key, base32-encoded into a file name |
| `AgentHUDCore/Providers/OpenAgents/OpenAgentCredentials.swift` | `SHA256.hash` → hex: hashed credential-to-account association |
| `AgentHUDCore/Providers/Codex/CodexDaemonOriginTransport.swift` | `Insecure.SHA1` of the WebSocket key (RFC 6455 `Sec-WebSocket-Accept`) |

Options:

1. **CNG** (`BCryptHash` with the `BCRYPT_SHA256_ALG_HANDLE` / `BCRYPT_SHA1_ALG_HANDLE` pseudo-handles, Windows 10+)
   through `WinSDK`. The pseudo-handles are C macros that cast an integer to a handle, which the Clang importer does
   not import, so they would have to be re-declared by value; error handling per call.
2. **Portable Swift implementation** (FIPS 180-4) of SHA-256 and SHA-1 in AgentHUDSupport, ~150 lines, no platform API.
3. `swift-crypto` — rejected: external package dependency.

## Evidence

In the spike (`spike-m0`, Windows, portable implementation): `RecordCodingTests.recordIdentitiesHaveUnambiguousComponents`
checks the SHA-256 of the empty input, and `ZstandardReaderTests` compares the SHA-256 of decoded Codex rollouts of
4–270 KB with digests that CryptoKit produced on macOS; both passed. The dedicated tests below come in M2.

## Decision

Option 2.

- `AgentHUDSupport/PortableDigest.swift` holds `PortableSHA256` and `PortableSHA1`, compiled on **every** platform so
  that the macOS test suite can compare them with CryptoKit byte for byte.
- `AgentHUDSupport/CryptoKitShim.swift`, compiled only where `CryptoKit` cannot be imported, declares
  `SHA256` and `Insecure.SHA1` with the subset of CryptoKit's API the code uses (`hash(data:)` returning a byte
  sequence). The four files above change only their import to `#if canImport(CryptoKit) import CryptoKit #endif`,
  so macOS keeps calling CryptoKit exactly as before.
- Verification:
  - NIST FIPS 180-4 / CAVP vectors (`""`, `"abc"`, the 448-bit and 896-bit messages, one million `"a"`) for both
    digests, on both platforms (`PortableDigestTests`).
  - On macOS only: 2,000 random inputs of lengths 0–300 bytes (every padding boundary) compared with CryptoKit.
  - Golden samples (`Tests/AgentHUDSupportTests/Fixtures/record-coding-golden.json`): `RecordCoding.hash` ids,
    encoder output and millisecond round-trips, checked byte for byte by the same test on macOS and Windows CI. The
    expected digests were computed independently with Python's `hashlib` and are then confirmed by the macOS run,
    which uses CryptoKit.

## Consequences

- Record ids are produced by different code on the two platforms; the golden test on both CI runners is what keeps
  them equal, so it must stay in both test runs.
- The implementation is not constant-time; it hashes identities and file names, never secrets that need side-channel
  resistance (the hashed OpenAgent association hashes a credential fingerprint locally, as on macOS).
