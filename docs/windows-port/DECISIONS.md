# Decisions

Choices made during the unattended Windows port (TASK.md §7). Architecture-level choices have an ADR in `adr/`; this
log records every choice, small or large, with the reason. Newest last. Revised entries keep their id.

| ID | Date | Milestone | Decision | Reason |
| --- | --- | --- | --- | --- |
| D-001 | 2026-10-16 | M0 | Architecture: Swift Support+Core on Windows, WPF shell, engine and shell talk over the engine's inherited stdio pipes (ADR-001). | Spike: Core and its tests compile and run on Windows without touching business logic. |
| D-002 | 2026-10-16 | M0 | UI: WPF on **.NET 10** instead of the brief's .NET 8 (ADR-002). | .NET 8 support ends 2026-11-10, within weeks; .NET 10 is the current LTS (to 2028-11) and is what the machine and `windows-latest` carry. |
| D-003 | 2026-10-16 | M0 | SQLite: the system `winsqlite3.dll` exposed as module `SQLite3` (ADR-003), with a version check before the ledger and the client-database reader use it. | No vendored source; `import SQLite3` unchanged in seven files; JSON functions present (3.51.1 here). |
| D-004 | 2026-10-16 | M0 | SHA-256/SHA-1: portable Swift implementation in AgentHUDSupport, CryptoKit-named shim only where CryptoKit is missing (ADR-004). | Deterministic ids; testable against CryptoKit on macOS; no dependency. |
| D-005 | 2026-10-16 | M0 | Shell↔engine transport is the engine's inherited standard input/output, not a named pipe `\\.\pipe\agenthud-<SID>-ui`. | Anonymous pipes inherited by one child cannot be opened by another process (no squatting, no DACL to get wrong) and tie the engine's life to the shell's (ADR-001). Hooks and `--mcp` still use named pipes. |
| D-006 | 2026-10-16 | M0 | Platform seam at **file granularity**: a macOS file replaced on Windows (`System/UnixSocket`, `UnixSocketListener`, `ChildProcess`, `FileChangeMonitor`, `InstanceLock`, `Providers/Codex/CodexDesktopIPC`) stays where it is and **is not edited at all** — not even its imports — and is excluded from the Windows build in `Package.swift`; its Windows twin of the same API lives in `Sources/AgentHUDCore/Platform/Windows/`. Other shared files get `#if os(Windows)` only around single statements or functions. | Zero diff in the macOS implementations, so upstream changes to them rebase cleanly; moving them into `Platform/Darwin/` (TASK.md M3 wording) would rename files upstream keeps editing. Consequence: nothing at compile time keeps a twin's API in step with its macOS file; the Windows CI build catches drift. |
| D-007 | 2026-10-16 | M0 | Windows builds run from an ASCII path. Locally the repository is at `E:\桌面项目\agent-hud-open` and builds go through the per-user junction `%LOCALAPPDATA%\agenthud-dev\src` with `--scratch-path %LOCALAPPDATA%\agenthud-dev\build`. `scripts/build-windows.ps1` (M8) will make such a junction itself under `%LOCALAPPDATA%` when the tree's path is not ASCII, and refuses an existing junction whose target is not this tree; when `%LOCALAPPDATA%` is itself not ASCII (a user name such as 张三), it uses an ASCII folder it creates with an owner-only DACL, checks the owner and target of one that exists, and otherwise stops with a message saying so. | Swift 6.4.1's clang driver fails to link a test DLL whose response files live under a non-ASCII path (the error text is lost too). A junction in a shared folder (a drive root) could be created or redirected by another user; one under `%LOCALAPPDATA%` cannot. |
| D-008 | 2026-10-16 | M0 | Folders: data `%APPDATA%\Agent HUD Open` (TASK.md §3), lock `%LOCALAPPDATA%\app.agenthud\instance.lock`. Each comes from its environment variable only when that holds an **absolute path to an existing folder**, else from `SHGetKnownFolderPath`. Foundation's `urls(for:)` is not used on Windows. | Foundation maps Application Support to `%LOCALAPPDATA%` and Caches to `%TEMP%` on Windows and traps when an override points at a missing folder; environment variables let tests use temporary folders; a relative or empty value would resolve against the working directory. Consequence: a copy started with a different `LOCALAPPDATA` takes a different lock — as on macOS a copy with another `HOME` would; the shell starts the engine with the session's environment. |
| D-009 | 2026-10-16 | M0 | Instance lock on Windows: the lock file held open for writing with `FILE_SHARE_READ` only (released by the system at exit or crash), holding `<executable path>\n<pid>`. No named mutex. `runningApplication(at:)` reads the file sharing everything and checks the pid still runs that executable. | The share mode is the Windows equivalent of `flock`; a mutex would be a second, possibly disagreeing source of truth; reading never blocks a starting copy. |
| D-010 | 2026-10-16 | M0 | Hook/MCP channels: named pipe `\\.\pipe\agenthud-<SID>-<24 hex>`, the hex an HMAC-SHA-256 of the lower-cased socket path keyed by a per-user secret kept in the data directory (`pipe.key`, 32 random bytes, created with `CREATE_NEW` and an explicit owner-only DACL rather than one inherited from the folder, never logged; a process that cannot read it does not connect, so the hook falls back to the client's own prompt); message mode, DACL `O:<SID>D:P(A;;GA;;;<SID>)`, `PIPE_REJECT_REMOTE_CLIENTS`, first instance with `FILE_FLAG_FIRST_PIPE_INSTANCE`; clients open with `SECURITY_SQOS_PRESENT|SECURITY_IDENTIFICATION` and talk only to a server process running as their own SID. | Keeps "only the user can reach it", "one process serves a path" and "a request is one message" (architecture.md) without file-system sockets. The server check defends against another user's pipe; the secret makes the name unguessable by another user, who could otherwise create it first and keep the engine from serving its hooks (they would fall back to the client's own prompt, a denial of service only). |
| D-011 | 2026-10-16 | M0 | Child processes: `CreateProcessW` with the executable path and an MSVCRT-quoted command line, quoting over **Unicode scalars** (a quote followed by a combining mark is still a quote); only the three standard handles inherited (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`); `CREATE_NO_WINDOW`; each child in its own job object; a `.bat`/`.cmd` extension (after trimming trailing dots and spaces, in any case) is refused, **and** the executable must be a PE image (`MZ` header) — both checks, since `CreateProcessW` picks `cmd.exe` by extension. `stop()` closes stdin, then after the 2 s grace terminates the job. | No shell string is ever built (G7); a batch file can only run through `cmd.exe`, whose parsing re-opens command injection (CVE-2024-24576 class); Windows has no SIGTERM. |
| D-012 | 2026-10-16 | M0 | `ps` and `lsof`: on Windows `ProviderCommand.run` answers the two fixed invocations Core makes (`/bin/ps -U … -o pid=,command=` and `/usr/sbin/lsof … -p <pid> -iTCP -sTCP:LISTEN -Fn`) from Toolhelp + `NtQueryInformationProcess` and `GetExtendedTcpTable`, in those tools' output format, current user's processes only, backslashes written as `/`. **Any other executable is refused** on Windows. | The readers and their tests (which inject that output) stay unchanged; no external program is run, and no POSIX path is ever resolved against a drive root. |
| D-013 | 2026-10-16 | M0 | `getuid()` exists on Windows and returns `UInt32.max`, which no file owner equals (the CRT reports owner 0). | Lets shared code that only *names* a user compile; any ownership check fails closed instead of passing. |
| D-014 | 2026-10-16 | M0 | Provider HTTP on Windows uses WinHTTP (`WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`, never a proxy for loopback), no redirects, no cookies, no WinHTTP auth, self-signed certificates accepted for `127.0.0.1` only; **a request is not sent when any of these options cannot be set** (fail closed); module `CWinHTTP` (system library, Windows only). | swift-corelibs URLSession lacks `bytes(for:)` and server-trust handling, and libcurl ignores the system proxy that macOS's URLSession follows; a credential must never follow a redirect. |
| D-015 | 2026-10-16 | M0 | Features without a documented Windows mechanism are compiled out behind their API and reported as unsupported: Codex Desktop IPC, the Codex daemon control socket, terminal/session jump (iTerm2), DeepSeek Harness process liveness. | TASK.md §7.2: never guess. |
| D-016 | 2026-10-16 | M0 | Transcript following in the permission hook polls the record every 250 ms on Windows. | No vnode events for an open handle on Windows; the read is incremental. |
| D-017 | 2026-10-16 | M0 | Sub-agents: `.claude/agents/port-reviewer.md` and `port-tester.md` are committed; this session runs from outside the repository, so it invokes them as general-purpose agents given the definition's text as their brief. Their limits (reviewer read-only; tester writes only reports) are therefore enforced by their instructions, not by tool restrictions; each report says what it wrote, and `git status` is checked after every run. | The agent registry is read from the session's working directory at start. |
| D-018 | 2026-10-16 | M0 | Preferences on Windows: `UsageAssembly`/`SettingsStore` get a `UserDefaults` subclass, `SettingsFile`, that keeps its values in `%APPDATA%\Agent HUD Open\settings.json` (demo: `settings.demo.json`; snapshot runs: in memory), written atomically (temporary file + `ReplaceFileW`). Only the calls the stores make are backed (`data`, `bool`, `set`, `removeObject`), with every `set` overload overridden so that none falls through to the CF domain; a test checks a round trip writes no `.plist`. | TASK.md §3. swift-corelibs `UserDefaults` writes `<suite>.plist` straight into `%LOCALAPPDATA%`. |
| D-019 | 2026-10-16 | M0 | Executables on Windows (`Providers/Kit/Executables.swift`, M4): a candidate is used only if it is an absolute drive or UNC path to an existing **PE image**; POSIX-absolute candidates (`/opt/homebrew/bin/…`, `/usr/local/bin/…`, `/Applications/…`) are compiled out of each locator on Windows; `PATH` is read without regard to the variable's case, split on `;`, empty and relative entries skipped, and each entry tried with `.exe` (never `.cmd`/`.bat`); a child's `PATH` is never extended with POSIX folders. | `URL(fileURLWithPath: "/opt/homebrew/bin/node")` resolves against the current drive's root, where any local user may create folders: another user could plant a program the HUD would run as this user (M0 review, BLOCKING). |
| D-020 | 2026-10-16 | M0 | The user's home on Windows is `%USERPROFILE%` when it holds an absolute path to an existing folder, else the profile folder of the process token. Core reads it through one function, `UserHome.directory` (`System/UserHome.swift`, M3), which on macOS **is** `FileManager.default.homeDirectoryForCurrentUser`; the 43 Core files that read the home call it instead, a one-line change each, and the boundary check rejects new direct uses in Core. That rule runs in macOS `make check` too, so an upstream change that reads the home directly fails the check on rebase until it is converted: accepted, it is the reminder the rebase needs. | `homeDirectoryForCurrentUser` ignores `USERPROFILE` on Windows, so a test (or an engine started by a test) could not be kept out of the real profile (G7, TASK.md §8). |
| D-021 | 2026-10-16 | M0 | Tests on Windows run with `APPDATA` and `LOCALAPPDATA` pointed at a fresh temporary profile folder (and `USERPROFILE` where a test needs a home); the gate commands in PROGRESS.md do this. | swift-corelibs `UserDefaults(suiteName:)` writes `<suite>.plist` into `%LOCALAPPDATA%`; a spike run left six such files and fifty temporary folders in the real profile (removed). Whether a temporary `LOCALAPPDATA` really redirects CoreFoundation is checked after each G3 run (no new `AgentHUDTests.*.plist` in the real `%LOCALAPPDATA%`) and recorded here. |
| D-022 | 2026-10-16 | M0 | The engine keeps its protocol output off file descriptor 1: at start it keeps the inherited stdout handle for the protocol and points the C runtime's and Foundation's standard output at standard error; the shell rejects any line that is not a valid message of the current protocol version (M6). | A stray `print` in shared code would otherwise inject protocol messages (M0 review). |
| D-023 | 2026-10-16 | M0 | Writing a client's settings file on Windows keeps the file's security descriptor: the new content goes to a temporary file in the same folder and replaces the old with `ReplaceFileW`, which keeps the original's ACL (M5); for a settings file kept as a link the replace targets the link's final path, and a first write, when no file exists, is a non-replacing move. Paths are compared without regard to case wherever Core matches paths (changed-path matching, client-home identities, log aliases, session projects) on Windows only (M3/M4). | "Keeping the file's permissions" means its ACL on Windows; an atomic rename would give it the folder's inherited ACL. Windows file systems are case-insensitive. |
| D-024 | 2026-10-16 | M1 | M1's "empty Core compile" is read as: the Windows CI installs the pinned toolchain, resolves the Windows package graph (Support only at this point), compiles and runs a smoke package against `WinSDK`, logs the image's `winsqlite3` version and runs the boundary check. Support's build and tests join the workflow in M2 and Core's in M3, each when it is green. | Support and Core need M2/M3's code to compile on Windows; a CI that fails until then would hide every other signal. |
| D-025 | 2026-10-16 | M1 | The Swift installer is downloaded from swift.org, pinned by SHA-256 (`9382E149…D91D59`, 2,097,955,608 bytes) and required to carry a valid Authenticode signature by Apple Inc. before it runs; it is cached by version and hash. No third-party setup action is used. | Supply-chain hygiene: swift.org publishes no detached signature for Windows installers since 5.9; the hash and signer are checked instead. |
